# 3. PROJECT OBJECTIVE

Build a system that intelligently forms project teams by considering multiple factors rather than simply randomly assigning students or grouping students by one attribute.

The system should optimize combinations of:

1. Technical skill coverage
2. Skill complementarity
3. Project requirements
4. Student project preferences
5. Availability
6. Work-style compatibility
7. Experience balance
8. Team diversity/balance
9. Fairness
10. Team-size constraints

The system must also explain **why** a particular team was formed.

The system should be positioned as:

> **A hybrid AI + optimization-based, explainable project team formation system.**

Do NOT make unsupported claims that the system can perfectly predict team success.

# 6. SKILL COMPLEMENTARITY

Do not simply group students who have identical skills.

Prefer teams where required capabilities complement each other.

Example:

Student A:

* Machine Learning

Student B:

* Backend

Student C:

* Frontend

Student D:

* Database

Student E:

* Presentation/Documentation

A strong team should cover the project's important skill areas.

Calculate both:

### Skill Coverage

How much of the required project skill set is covered?

### Skill Complementarity

How well do different members fill different capability gaps?

Avoid producing teams containing many students with the same skill while leaving important project requirements uncovered.

# 12. CONSTRAINED OPTIMIZATION

Do not rely solely on K-Means or another clustering algorithm.

The team formation problem contains constraints and should use an appropriate optimization approach.

Potential techniques include:

* greedy optimization
* Hungarian algorithm where appropriate
* integer programming
* constraint programming
* optimization libraries
* clustering as a preprocessing step
* semantic similarity
* embeddings
* hybrid scoring + optimization

Select the simplest technically justified approach.

Do not use an algorithm merely because it sounds more "AI."

---

# 13. HARD CONSTRAINTS

The system should support constraints such as:

* required team size
* each student assigned at most once
* each student assigned to exactly one team when appropriate
* required project skills
* locked student assignments
* excluded student combinations where faculty explicitly specifies them
* availability requirements where configured

Hard constraints must not be silently violated.

---

# 14. SOFT CONSTRAINTS

Support weighted preferences such as:

* project preference
* availability quality
* work style
* skill similarity
* skill diversity
* experience balance
* student preferences

Soft constraints may be traded off according to configurable weights.

---

# 15. FAIRNESS

Prevent the system from simply creating:

> Team 1 = all strongest students
> Team 2 = everyone else

Consider:

* academic/experience balance where appropriate
* skill distribution
* project preference distribution
* workload distribution
* availability
* capability diversity

Do not use protected or sensitive personal characteristics for unfair ranking.

---

# 16. CONFLICT DETECTION

Before finalizing teams, identify issues.

Examples:

### Schedule Conflict

"Two members have no common collaboration period."

### Skill Gap

"No member has sufficient database capability."

### Preference Conflict

"Three members selected the same project as their first preference."

### Team Imbalance

"Most required technical skills are concentrated in one member."

### Constraint Conflict

"Current locked assignments prevent complete skill coverage."

Display these clearly.
